# Database security ? Phase 2 proposal

The authoritative proposal is `supabase/proposals/consolidated-initial.sql`, outside automatic migrations and **unapplied remotely**. Read the [complete pre-migration report](phase2-pre-migration.md) for its exact table inventory, relationships, indexes, functions/triggers, role/table matrix, bootstrap, review findings, acceptance tests and future apply command. Phase 2A inspected remote metadata strictly read-only and tested the proposal in disposable local Supabase; see the [validation report](phase2a-validation.md).

Every business row has an organization, immutable creator/identity and restrictive cross-tenant foreign keys. Scoped RLS uses verified active database memberships and seeded canonical capabilities, with deny/expiry handling and optional Owner/admin AAL2. Protected membership/role/override tables have no direct API write grants. The only member-change RPC requires a verified Owner, recent password authentication, confirmation and a reason; it rejects self and Owner targets. Owner memberships are immutable; deferred transactional checks also prohibit an ownerless organization.

Audit/version history is append-only to API roles. Business writes append minimal mutation metadata in the same transaction. SQL definer functions use qualified relations, pinned search paths and narrow grants. A future-table event trigger enables/forces RLS and revokes implicit API access. Its execution passed on local Supabase PostgreSQL 17.11 with matching relevant hosted migration-role privileges; remote application remains separately approved. The service credential is server-only and used exclusively by the disabled-by-default bootstrap route; ordinary business adapters use the user's session and RLS.

Initial bootstrap authenticates a verified user matching server-only `INITIAL_OWNER_EMAIL`, then uses a service-only RPC with a locked singleton to atomically create the organization, seeded roles/permissions, Owner and audit. Same-user retries are idempotent. No password, owner email or real organization is seeded in SQL. Bootstrap has run only with synthetic local fixtures.

`supabase/config.toml` is **local development configuration**, not a statement about hosted security. Hosted development and future production require public signup off, verified email, password minimum 12 with upper/lowercase/digit/symbol, approved redirect URLs, tested reset/invitation delivery and rate controls. MFA enrollment/challenge/recovery must be implemented before optionally enabling Owner/admin enforcement. No hosted Auth settings have been changed.

Remaining production work: restricted invitation/custom-role/override management, production auth flows, transactional import/undo/conversion/publication, conflict detection, service restrictions and tested backup/recovery. The [report](phase2-pre-migration.md) distinguishes SQL guarantees proposed from behavior actually verified. No production use or migration without explicit approval.

Reference: [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security) and [SSR authentication](https://supabase.com/docs/guides/auth/server-side/creating-a-client). Platform documentation does not certify this proposal.
